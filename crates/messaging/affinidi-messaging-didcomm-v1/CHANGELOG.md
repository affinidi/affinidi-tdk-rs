# affinidi-messaging-didcomm-v1 changelog

## 0.1.1 — 8th August 2026

Manifest fix. No code change.

- **Require `affinidi-messaging-core` 0.1.6, not 0.1.** The optional
  `messaging-core` feature compiles `adapter.rs`, which names
  `Protocol::DIDCommV1` — a variant that only exists from 0.1.6. The published
  0.1.0 asked for `"0.1"`, which resolves to 0.1.6 on a fresh build (so publish
  verification was green) but lets a consumer with an existing lockfile, or one
  pinning `--precise 0.1.5`, fail with `no variant named DIDCommV1`.

  The general shape is worth noting: when an optional feature depends on an API
  added in the *same release train*, a loose minor requirement only looks
  correct because no stale lockfile exists yet.

## 0.1.0 — 8th August 2026

Initial release: DIDComm v1 (Aries RFC 0019) transport primitives, alongside the
existing DIDComm v2.1 support in `affinidi-messaging-didcomm`.

### Added

- **Envelope** — RFC 0019 pack/open for authcrypt and anoncrypt, with the NaCl
  primitives it is specified in terms of (`crypto_box`, `crypto_box_seal`,
  ChaCha20-Poly1305 IETF) implemented over `x25519-dalek` 3, `salsa20`,
  `crypto_secretbox` and `chacha20poly1305`. The RustCrypto `crypto_box` crate
  was deliberately not used: it depends on `curve25519-dalek` 4 and would put a
  second dalek generation in the workspace graph.
- **`UnpackResult`** — authcrypt, authcrypt-from-an-unbound-key, anoncrypt and
  plaintext as disjoint variants, plus `require_authenticated()` as a one-call
  transport gate. There is no `Option<Did>` for a caller to unwrap carelessly.
- **`MessageV1`** — `@id` / `@type` with a flattened top-level body, and the
  `~thread` decorator preserving the absent-vs-defaulted `thid` distinction.
- **`Did` / `Verkey`** — bare-DID normalisation for exact string comparison, and
  base58 Ed25519 verkeys with X25519 derivation.
- **Protocols** — Basic Message 1.0 (RFC 0095) and Forward 1.0 (RFC 0094).
- **`DIDCommV1Agent` / `DIDCommV1Store`** — mirroring the v2.1 `DIDCommAgent` and
  `DIDCommStore`, with the verkey → DID index v1 unpack requires.
- **`messaging-core` feature** — `DIDCommV1Adapter` implementing
  `MessagingProtocol`, so v1 and v2.1 can be driven through one trait object.

### Interop

Verified in both directions against **Credo 0.6.3 / askar 0.4.3**:

- Credo → this crate: 12 tests in `tests/credo_interop.rs` against committed
  envelopes generated by a live Credo agent's `DidCommEnvelopeService`.
  Runs in CI; needs no Node.
- This crate → Credo: 5/5 envelopes opened by Credo's own decryption path
  (authcrypt, anoncrypt, no-thread, multi-recipient, mediator forward), via the
  developer harness in `interop/didcomm-v1`.

### Wire-format notes for implementers

Three findings from that interop work, each pinned by a test:

- The protected header's `enc` is **`xchacha20poly1305_ietf`, and it is a
  misnomer** — the AEAD is ChaCha20-Poly1305 IETF with a 12-byte nonce.
  Implementing what the header says yields envelopes no Aries agent can open.
- `crypto_box` output is `MAC || ciphertext` (libsodium order); the RustCrypto
  AEAD convenience API appends the tag instead.
- v1 message types have **two interchangeable document URIs**,
  `did:sov:BzCbsNYhMrjHiqZDTUASHg;spec` and `https://didcomm.org`. Credo emits
  the latter by default — including for `routing/1.0/forward` — while most
  specification examples show the former. Use `types_match`, not `==`.
- Anoncrypt recipient headers **omit** `sender` / `iv` in Credo's output, where
  RFC 0019's example and older indy-sdk use explicit `null`s. Both are accepted;
  omission is emitted.

### Publishing

This crate has never been published, so its first version must be
`cargo publish`ed by a human — CI's Trusted Publishing cannot create a new
crates.io entry (403).
