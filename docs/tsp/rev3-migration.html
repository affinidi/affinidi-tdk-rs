TSP Rev 3 Migration

Rev 3 of the Trust Spanning Protocol deletes the HPKE mode our crypto layer implements and rewrites every payload layout we emit. This is what changed, what it costs us, and the order to do it in.

The finding

Rev 3 removes HPKE-Auth, which is the only mode we implement. src/crypto/hpke.rs is MODE_AUTH = 0x02 throughout — auth_encap, auth_decap, the two-DH KEM. The spec's first Rev 3 commit is “Remove HPKE_Auth mode and update”, and the normative text is now “TSP implementations MUST support HPKE-Base mode”. The 4G–9G ciphertext codes are struck from the CESR table.

There is no partial-compatibility path. The envelope layout, the ciphertext code, the AAD and info inputs, and all five payload layouts change together, so a message is either wholly Rev 2 or wholly Rev 3. Everything below follows from that.

The mitigating fact is that the reference SDK has already done this work in the open across four well-documented PRs, and our crate is a deliberate port of theirs. Their sequencing is a tested migration order, not a guess — the plan at the bottom of this page mirrors it.

What changed

The break is concentrated in the crypto binding and the CESR frame

Cryptography (§8)

  • HPKE-Base only. Sender authentication moves entirely to the signature plus an AAD binding — the receiver no longer proves the sender held a KEM private key.
  • aad becomes CONCAT(TSP_Version, VID_sndr, VID_rcvr), passed as real AEAD associated data. info becomes the literal CESR code YTSP-. TSP_Tag is explicitly excluded from the AAD.
  • Ciphertext is CONCAT(enc, ct) with the AEAD tag inside ct.
  • Non_Confidential_Fields is deleted throughout. A message is now entirely confidential or entirely signed-only, never mixed.
  • The ESSR sender-VID payload field is mandatory under Sealed Box and optional-but-must-match under HPKE-Base — but the field is always present, defaulting to the NULL VID 4BAA.
  • Post-quantum is no longer a separate mode: HPKE-Base with KEM X25519MLKEM768 (0x647a), chosen by the recipient VID's key type, on the same wire codes. ML-DSA-65 signatures added as 1AAQ (provisional, pending CESR issue #14).
  • Sealed Box: the crypto_box_seal_open description is corrected to take the receiver's public key.

Encoding (§9)

  • Long-form count codes change from -0X##### to --X#####. The -0 form belonged to a superseded draft of the v2 tables.
  • The master code table moves from --AAACAA to -_AAACAA, genus AAA v2.00.
  • Every payload layout is rewritten to one shape: type code, then VID_sndr | 4BAA, then type-specific fields, then a mandatory Padding_Field last.
  • XRFI collapses to a single layout that gains Reply_Path and Referral_Field; XRFA to a single layout with no referral; XRFD loses its nonce.
  • Nonce is 128-bit under code 0A.
  • The Ed25519 signature moves inside an indexed group as B#, and the -C/-K counts become length-based.
  • TSP_Digest becomes a true self-addressing identifier, computed over the message's own version, both VIDs and plaintext payload with the digest's own slot filled with 0x23 dummy bytes — excluding the -E/-Z tags, the padding field and Signature_new. Receivers recompute and reject on mismatch.
  • XSCS/XCTL carry application data as a -A## generic CESR stream; non-native JSON, CBOR or MsgPak must sit inside -H## groups rather than being freely interleaved.
  • Canonical padding is mandatory — a receiver MUST reject non-canonical pad bits, since digests and signatures are taken over exact bytes.

Protocol behaviour (§3, §5, §7)

  • A route's exit entry is the destination's VID, not the intermediary's — VID_q1 became VID_b1 throughout §5.
  • New general invalid-message rule: discard silently, send no response, do not act. Within an established relationship, re-resolve the sender's VID and retry verification once. Rate-limit resolution. Suspend reliance on key state that conflicts rather than extends.
  • VIDs for public use MUST support rotation and provenance verification, and rotation authority MUST be separate from the signing key.
  • Key rotation preserves relationships — a relationship is a VID pair, not a key pair — and there is deliberately no TSP control message for rotation.
  • The Route Info section is deleted; a large, mostly informative Security & Privacy section is added.

Not built at all

Newly required, or newly specified, and absent from our crate

Signed-only messages
Non-confidential frames with no ciphertext. -S## is gone; these are just -E frames without a ciphertext field.
XCTL
Generic control payload carrying an opaque upper-layer stream.
XPAD & padding
Padding messages and the caller-visible padding field that every layout now ends with.
Reply_Path
Routed relationship forming. The reference has not built this either — it is the next piece of work on their side.
Referral_Field
A new VID plus its own signature, introduced over an existing relationship.
Sealed Box
Libsodium anonymous sealed box, code 4C. The spec says implementors SHOULD migrate away from it; low priority.
X25519MLKEM768
PQ/T hybrid KEM 0x647a. Realistically arrives with the hpke crate rather than by hand.
ML-DSA-65
Post-quantum signatures under the provisional code 1AAQ.

Plan

Four phases on a long-lived branch, mirroring the reference's tested order

The spec PR is still open, test vectors are explicitly deferred until after review, and 1AAQ is provisional — so byte-level details can still move. Keep main on Rev 2 until tsp-sdk cuts a Rev 3 release, and do the work on a rev3 branch that tracks theirs.

01

CESR wire format

Envelope, payload and signature encoding. Long-form count codes, XAAA removal, the single -E frame covering ciphertext, the unified payload layouts with VID_sndr first and padding last, byte-length hop counts, the indexed signature code, mandatory signature attachment, canonical padding enforcement, receive-side size limits.

mirrors tsp-sdk #332
02

Crypto

HPKE-Base with the real AAD and YTSP- info, the enc‖ct layout and the 4F code; removal of the non-confidential data field; the self-referencing digest replacing our out-of-band payload hash. Swap the hand-rolled HPKE for the hpke crate here, and bring over known-answer tests against the RFC 9180 A.2 and draft-ietf-hpke-pq vectors — the reference used them to confirm the tag-inside-ct convention, and they are the cheapest possible check that we got the binding right.

mirrors tsp-sdk #333
03

Protocol behaviour

Relationship gating, the RFI race tiebreak, RFD semantics, key-state staleness with re-resolve-and-retry plus rate limiting, the route exit as the destination's VID, and silent discard with no response. This phase touches the mediator and the SDK, not just the crate.

mirrors tsp-sdk #335
04

Spec resync

Reconcile against wherever PR #63 has landed by then, re-point the interop harness at the released tsp-sdk, and get back to a green matrix in both directions across all four message types. Update docs/tsp/interop.md, which currently claims full interoperability against 0.9.0-alpha2.

mirrors tsp-sdk #336

Two things worth landing on main now

Both are correct under Rev 2 as well as Rev 3, so neither has to wait for the branch:

  • Uniform mediator responses on TSP failure. Return one acknowledgement whatever went wrong and log the reason locally, instead of three distinguishable status codes.
  • Canonical padding rejection in the decoder. Reject non-zero lead bytes rather than skipping them.

Blast radius

The crate is consumed by the mediator (handlers/authenticate/tsp.rs, message_inbound.rs, websocket.rs, messages/inbound.rs), the SDK (protocols/tsp.rs, tsp_wire.rs, tsp_auth.rs), the affinidi-tdk facade, the DIDComm v1 adapter, and the test-mediator TSP test suite.

Most of the change is internal to affinidi-tsp, so consumers largely see stable signatures — with one exception that matters: the thread digest is a public field on PackedMessage and UnpackedMessage and is what the relationship FSM correlates on. Changing it from an out-of-band hash to a verified on-wire SAID is a source-visible change.

Per ADR 0003 and the version-collision trap we have hit repeatedly: run check-workspace-duplicates.sh on the version bumps, and note that a behavioural change to send/receive semantics is breaking for consumers even where signatures hold — R3.6 applies, and this one is breaking on the wire as well.
